## 0. 先分清三张表的职责

群聊相关有四张表，但职责是分开的，别混：

| 表 | 管什么 | 一句话 |
|---|---|---|
| `group_info` | 群这个实体本身（群主、群名、状态、创建时间） | 群档案 |
| `user_contact` | 我和这个群**有没有关系 / 有什么权限** | 关系与权限 |
| `chat_session` | 会话主表（sessionId、最后一条消息、最后时间） | 会话内容 |
| `chat_session_user` | **我视角**下的会话（联系人名、会话 ID） | 会话展示视角 |

关键点：**`chat_session_user.contact_name` 是冗余字段**。前端会话列表和聊天窗口顶部的群名，全部从这里取，**不查 `group_info`**。

```js
// ChatSession.vue:8   会话列表
<div class="user-name">{{ data.contactName }}</div>

// Chat.vue:33         聊天窗口顶部
<span>{{ currentChatSession.contactName }}</span>
```

只有点"群详情"弹窗时，前端才调 `/group/getGroupInfo4Chat` 去查 `group_info`（`ChatGroupDetail.vue:69`）。

## 1. `loadContact` 里 `.in(status, 1, 3, 5)`，群聊怎么过滤？

**不用为群聊单独写过滤条件——`contactType` 这一层已经把用户和群分开了。**

看源项目的写法（`UserContactController.java:95-120`）：status 数组是在 `if/else` **之后**统一设置的，USER 和 GROUP **共用同一组状态**：

```java
if (UserContactTypeEnum.USER == contactTypeEnum) {
    contactQuery.setQueryContactUserInfo(true);       // 补用户昵称/性别
} else if (UserContactTypeEnum.GROUP == contactTypeEnum) {
    contactQuery.setQueryGroupInfo(true);             // 补群名
    contactQuery.setExcludeMyGroup(true);             // 排除我创建的群
}
// ↓ 两个分支共用，没有按类型再分
contactQuery.setStatusArray(new Integer[]{
        UserContactStatusEnum.FRIEND.getStatus(),         // 1
        UserContactStatusEnum.DEL_BE.getStatus(),         // 3
        UserContactStatusEnum.BLACKLIST_BE.getStatus()}); // 5
```

复刻项目（`UserContactServiceImpl.java:188-239`）同样是先按 `contactType` 过滤，再在同一个查询里带 `{1, 3, 5}`：

```java
.eq(UserContact::getContactType, contactType.getType())
.in(UserContact::getStatus,
  UserContactStatusEnum.FRIEND.getStatus(),        // 1
  UserContactStatusEnum.DEL_BE.getStatus(),        // 3
  UserContactStatusEnum.BLACKLIST_BE.getStatus())  // 5
```

### 1.1 为什么群聊下带 3、5 也没问题

因为 `contactType = GROUP` 时，`user_contact` 里根本不存在 status=3 或 5 的群记录：

- **3（被好友删除）/ 5（被好友拉黑）** 这两个状态的语义是"**好友**单方面改了关系"，只在 `contactType = USER` 的场景下产生
- 群记录只会是：1（正常在群）、2（解散时的全员标记）

所以多带两个值，在群分支里"查不出多余的行"，代价为零。反过来如果给群单独写一套 `{1}`，反而和源项目行为不一致，没必要。

> 真正的群差异不在 status，而在后面两件事：
> ① 批量查 `group_info` 补群名；
> ② `removeIf` 排除"我创建的群"（我建的群在"我创建的群"里展示，不在"我加入的群"里重复出现）。

## 2. 被踢出群，status 是多少？

**没有 status——被踢和主动退群，记录是物理删除的，行直接没了。**

源项目 `leaveGroup`（`GroupInfoServiceImpl.java:338-392`）：

```java
Integer count = userContactMapper.deleteByUserIdAndContactId(userId, groupId);   // ← DELETE
```

对应的 Mapper XML（`UserContactMapper.xml:315-320`）：

```xml
<delete id="deleteByUserIdAndContactId">
    delete from user_contact
    where user_id = #{userId}
      and contact_id = #{contactId}
</delete>
```

`addOrRemoveGroupUser` 的踢人分支只是复用了同一个方法，消息类型换成 `REMOVE_GROUP`：

```java
if (opType == 0) {
    leaveGroup(contactId, groupId, MessageTypeEnum.REMOVE_GROUP);   // 踢人
} else {
    addContact(...);                                                // 拉人
}
```

所以：

| 场景 | user_contact 里的变化 | loadContact 还能查到吗 |
|---|---|---|
| 主动退群 | 我的那一行被 DELETE | 查不到 → 群从"我加入的群"里消失 |
| 被踢出群 | 我的那一行被 DELETE | 查不到 → 同上 |
| 群被解散 | 全员 status 改成 2（DEL），行**保留** | 查不到（status 不在 {1,3,5} 里） |

**注意：退群/踢人是"我的单向删除"，不是双向。** 好友删除要写两条（我→TA、TA→我），但群不需要——群对每个人只有"我这一个视角"，删掉我这一行就完事了。

## 3. 为什么退群/踢人必须物理删除，解散却用软删？

不是随意设计，**退群/踢人有两个硬约束逼着你物理删除**。

### 3.1 约束一：联合主键挡住"重新入群"

`user_contact` 的主键是 `(user_id, contact_id)`。如果退群只是把 status 改成 2 保留行，那么这个人**再次加入同一个群**时：

```sql
INSERT INTO user_contact (user_id, contact_id, ...) VALUES ('U123', 'G456', ...);
-- ❌ Duplicate entry 'U123-G456' for key 'PRIMARY'
```

要支持软删，就必须像加好友那样自己写"先查后写"的 upsert（本项目 `saveOrUpdateContact` 就是这么干的）。而群成员关系走的是 `addContact` 的群分支，路径不同，没必要为它专门再写一套 upsert。

**物理删除直接绕开这个问题**：删干净了，再 INSERT 天然不冲突。

### 3.2 约束二：成员数统计口径会把退役成员算进去

源项目和复刻项目的成员数都是这么算的（`GroupInfoServiceImpl.countMember`，注释写明"源项目口径"）：

```java
/** 群成员数（源项目口径：user_contact 里 contact_id=群 的记录总数，不限状态） */
private Integer countMember(String groupId) {
    Long count = userContactMapper.selectCount(
      new LambdaQueryWrapper<UserContact>()
        .eq(UserContact::getContactId, groupId));
    return count == null ? 0 : count.intValue();
}
```

**没有 status 条件。** 如果退群/踢人留了 status=2 的行，群里明明只剩 3 个人，详情页会显示"10 人"。要软删就必须同步改这个统计口径——一个改动牵出另一个改动。

### 3.3 解散群为什么可以软删

解散群**没有上面两个约束**：

- **群不会"复活"**：`groupId` 是建群时生成的一次性 ID，解散后没有人会再用同一个 ID 重新 INSERT `user_contact`，主键冲突不存在
- **成员数没人看**：群都解散了，没人会去打开群详情看人数；`checkGroupAndGet` 也会因为 `group_info.status=0` 直接抛"群聊不存在或已经解散"

源项目 `dissolutionGroup`（`GroupInfoServiceImpl.java:296-336`）就是两步 UPDATE：

```java
GroupInfo updateInfo = new GroupInfo();
updateInfo.setStatus(GroupStatusEnum.DISSOLUTION.getStatus());   // 群 → 0
this.groupInfoMapper.updateByGroupId(updateInfo, groupId);

UserContact updateUserContact = new UserContact();
updateUserContact.setStatus(UserContactStatusEnum.DEL.getStatus());   // 全员 → 2
userContactMapper.updateByParam(updateUserContact, userContactQuery);
```

> 实现细节提醒：源项目是"先 UPDATE 全员为 2，**再** `selectList(userContactQuery)` 把全员 userId 捞出来清 Redis 缓存"。
> 如果哪天改成物理删除，**顺序必须反过来**：先查出 userId 列表 → 再 delete → 再清缓存，否则删完就查不到人了。

## 4. 解散群时把 `group_info` 和 `user_contact` 直接删掉，行不行？

**功能上基本能跑通，但没有任何收益。**

### 4.1 先验证前端依赖

| 展示位置 | 数据来源 | 硬删 group_info 会怎样 |
|---|---|---|
| 会话列表群名 | `chat_session_user.contact_name`（冗余） | 不受影响 |
| 聊天窗口顶部 | `currentChatSession.contactName`（冗余） | 不受影响 |
| 群详情弹窗 | `/group/getGroupInfo4Chat` 查 `group_info` | 弹"群聊不存在或已经解散" |

关键是第三行：**软删（status=0）和硬删在弹窗里的表现完全一样**。`checkGroupAndGet` 里无论是查不到、还是 status≠1，抛的都是同一句话：

```java
if (groupInfo == null || !GroupStatusEnum.NORMAL.getStatus().equals(groupInfo.getStatus())) {
    throw new BusinessException("群聊不存在或已经解散");
}
```

前端 `ChatGroupDetail.vue:69-80` 的处理也只是弹提示，不会崩溃：

```js
errorCallback: (response) => {
  proxy.Confirm({ message: response.info, showCancelBtn: false })
}
```

**所以"群详情弹窗会报错"不能作为支持软删的论据——两种做法都报错。**

### 4.2 软删真正的收益（成本都为零）

UPDATE 一行和 DELETE 一行，在索引开销上是一样的。**成本相同的情况下，保留信息的那条路更好**：

**① `chat_message` 不会变成孤儿数据**

`chat_message.contact_id = groupId` 的历史消息是永久保留的，不会因为解散被删。`group_info` 硬删之后，这批消息就指向一个不存在的实体。以后要做"导出群聊记录""群消息审计""用户投诉某个群"这类功能，数据链已经断了。软删的话 `selectById(groupId)` 至少还能查回来。

**② 成员构成可追溯**

`user_contact.status=2` 保留了"谁曾经在这个群里"。硬删就永久丢失——用户问"我以前那个群怎么没了"，连查都查不了。

**③ 和枚举语义一致**

`GroupStatusEnum` 定义了 `DISSOLUTION(0, "解散")`，`UserContactStatusEnum` 定义了 `DEL(2, "已删除好友")`。这些枚举值存在的意义就是"用状态表达生命周期"，不是摆设。用它们，和好友删除（status=2/3）的处理方式也是统一的。

### 4.3 硬删想省的那点存储，可以忽略

| 表 | 解散时新增的数据量 |
|---|---|
| `group_info` | 1 行 |
| `user_contact` | 群成员数（撑死几十上百行） |
| 对比 `chat_message` | 每天几千上万行 |

这点数据在存储上完全可忽略。如果真在意，加个定时任务清理三年前 `status=0` 的群即可，不影响主流程。

### 4.4 结论

> **退群/踢人硬删，是被两个硬约束逼出来的；解散软删，是成本相同时选了信息更多的那条路。**
> 两类场景的差异有具体技术原因，不是随意设计。

## 5. 一页速查

| 问题 | 答案 |
|---|---|
| `loadContact` 群聊怎么过滤 status | 不用单独处理，USER/GROUP 共用 `{1,3,5}`，靠 `contactType` 区分 |
| 群记录会出现 status=3、5 吗 | 不会，3/5 是好友关系的状态，只对 USER 有意义 |
| 被踢出群 status 是多少 | 不是 status，行被**物理 DELETE**，查不到 |
| 主动退群呢 | 同样是物理 DELETE，只删"我"这一行（单向） |
| 退群为什么不能软删 | ① 联合主键 `(user_id, contact_id)` 挡住重新入群；② `countMember` 不限 status 会把退役成员算进去 |
| 解散为什么可以软删 | 群 ID 不会复用（无主键冲突），成员数没人看（无统计口径问题） |
| 解散时 `group_info` 能硬删吗 | 前端能跑通（群名来自 `chat_session_user.contact_name`），但会丢历史消息的实体引用和成员构成，且没有收益 |
| 群名到底从哪来 | `chat_session_user.contact_name` 冗余字段，**不查 group_info** |
| 群详情弹窗查哪张表 | `/group/getGroupInfo4Chat` → `group_info`，软删硬删都报"群聊不存在或已经解散" |
