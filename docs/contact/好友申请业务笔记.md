## 一、业务数据流向总览

### 1. /contact/search（搜索查人）
```
前端按完整用户ID(U开头)发起
  → 从ID前缀判断 U=用户 / G=群 (getByPrefix)
  → user_info 按ID精确查一个人
  → CopyTools 把 UserInfo 拷成 UserContactSearchResultDto
  → 查 user_contact(我→TA) 拿关系状态 status
  → 返回给前端（找不到人返回 null，前端自己显示"查无此人"）
```

### 2. /contact/applyAdd（发起申请）
```
前端传 contactId(要加谁) + contactType("user") + applyInfo(附言)
  → 校验 contactType
  → 附言空则填默认 "我是{我的昵称}"
  → 查"我→TA"记录：若 status 是 5/6(被对方拉黑) → 拒绝
  → 查对方 user_info 拿 joinType(0直接加入/1需要审核)
  → joinType=0 → 直接建好友（TODO，下闭环做）
  → joinType=1 → 按唯一索引写/更新 user_contact_apply(status=0待处理)
  → 仅"新申请/上次已处理"时 WS 推 CONTACT_APPLY(4) 给接收人
```

## 二、关键 Q&A（踩坑点）

### Q1：为什么后端 /search 不做模糊搜索？
EasyChat 的搜索框模糊匹配是**前端拿本地联系人数据**做的；用户输入完整用户ID回车后，才调后端 `/contact/search`。
后端只认完整ID，所以用 `UserContactTypeEnum.getByPrefix(contactId)`：
- `Uxxxx` → USER
- `Gxxxx` → GROUP
- 其他前缀 → 返回 null

**`getByPrefix` 和 `getByName` 的区别**：
- `getByName("user")`：按枚举名字（USER/GROUP）找，用于前端传字符串类型；
- `getByPrefix("Uxxx")`：按ID首字母找，用于从完整ID反推类型。

### Q2：为什么判断"对方拉黑我"，查的是我自己这条 user_contact？
对方拉黑我时，数据库里**我这条记录**（user_id=我, contact_id=TA）的 status 会被改成：
- `BLACKLIST_BE(5)` 被好友拉黑
- `BLACKLIST_BE_FIRST(6)` 首次被好友拉黑

所以只查一条"我→TA"的记录，看它 status 在不在 {5,6} 里，就知道我有没有被拉黑——不用反查对方视角的记录。
（对比：我拉黑对方，是"我→TA"这条记录 status=BLACKLIST(4)。）

### Q3：重复点"加好友"为什么不会产生多条申请？
`user_contact_apply` 表有唯一索引 `(apply_user_id, receive_user_id, contact_id)`：
- 先 `selectOne` 查旧记录；
- 没有 → insert 新申请；
- 有 → 把 status 打回 INIT(0)、更新 last_apply_time 和 apply_info，走 updateById。
就算对方上次拒绝过(2)，重新申请就变成待处理(0)。

### Q4：WS 推送为什么要加 `dbApply == null || !INIT.equals(dbApply.getStatus())` 判断？
如果上一条申请还是"待处理"，对方还没看，就**不重复推**，避免打扰。
只有"全新申请"或"上次申请已处理完(同意/拒绝/拉黑)"时才推 CONTACT_APPLY(4)。

### Q5：CopyTools.copy(UserInfo → DTO) 之后为什么还要手动补 iconLastUpdateTime？
本项目 `UserInfo.lastLoginTime` 是 `Date`，而 DTO 的 `iconLastUpdateTime` 是 `Long`——同名不同类型，BeanUtils 拷不过去，必须手动：
```java
dto.setIconLastUpdateTime(u.getLastLoginTime() == null ? 0L : u.getLastLoginTime().getTime());
```
（源项目里 UserInfo 这字段本来就是 Long，复刻时我们按自己表结构做了 Date，这里要适配。）

### Q6：搜索结果里"查无此人"和"陌生人"怎么区分？
- 查不到 user_info → **整个 DTO 返回 null**（前端显示无此人）；
- 查到人但 user_contact 没记录 → DTO 正常返回，**status 给 null**（不是 0！和源项目保持一致）；
- 搜到自己 → status 直接给 FRIEND(1)。

### Q7：joinType 是什么？为什么要返回给前端？
`user_info.join_type`：
- 0 = JOIN 直接加入（不用审核，点加好友立刻成好友）
- 1 = APPLY 需要审核（写申请，等对方同意）

applyAdd 把它 return 给前端，前端据此提示"已发送申请"还是"你们已经是好友了"。
当前测试号 join_type 都是 null/1，所以走"写申请记录"分支；joinType=0 的直接建好友分支留了 TODO，和下一个闭环"同意申请"共用同一个 `userContactService.addContact(...)`（双向建好友关系）。
