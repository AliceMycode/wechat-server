# 新工程重设计要点

> 背景：当前 `wechat-server` 沿用原 easychat 的库表结构，先保持现状只做现有功能收尾。
> 下一版新工程（已有服务器 / 阿里云 OSS / CDN）重设计表结构，并新增消息撤回、消息删除、消息引用、朋友圈、收藏夹。
> 本文记录当前工程暴露出、值得在新工程一次性解决的问题，**当前工程不为此做预埋式重构**。

---

## 1. 消息表要支持撤回 / 删除 / 引用

当前 `chat_message` 只有 `messageContent / messageType / status`（status 仅表示发送中/已发送），无法承载：

| 功能 | 需要的能力 |
|---|---|
| 消息撤回 | 消息状态位（正常/已撤回）+ 撤回时间 + 撤回操作人 |
| 消息删除 | 区分「只删我这边」和「双方都删」：会话级删除用 per-user 可见性表，双方删除才改消息本体 |
| 消息引用 | `quote_message_id` 指向被引用消息；被引用消息撤回后仍要能显示出「原文已撤回」占位 |

要点：

- 撤回不要物理删，改状态位，否则引用链断掉、多端同步也没法描述。
- 「只删我这边」不能动 `chat_message`，需要有 `chat_message_user` 之类的可见性/删除标记表（`user_id + message_id + deleted`）。
- 引用记录的是 messageId 而不是内容快照；展示时再 join 原文，撤回后原文变占位符。

---

## 2. `MessageSendDto.contactId` 一字段两用

当前 `contactId` 在不同阶段含义不同：

- service 组装时 = **路由目标**（消息要发给谁 / 群 ID）
- `ChannelContextUtils.sendMsg` 推给前端前被**覆写**成**会话对象**（单聊时是发送人、群聊时是群 ID）

后果：看代码要靠上下文判断此刻的 `contactId` 是哪一种语义，注释与代码已出现过不一致（`saveMessageFile` 处）。

新工程拆成两个字段：

- `receiveUserId` —— 路由用，只在服务端内部流转
- `contactId` —— 会话对象，从头到尾语义唯一，推给前端的永远是它

这样可以彻底删掉 `sendMsg` 里的覆写分支和 `ADD_FRIEND_SELF` 那种特例。

---

## 3. 未读数只存在前端本地

当前未读数是纯前端概念，存在 Electron 本地 SQLite `chat_session_user.no_read_count`，服务端 `chat_session_user` 只有 `user_id, contact_id, session_id, contact_name` 四列。

问题：

- 多端登录时各端未读数各自为政，无法同步
- 未读上报、跨端已读、消息漫游都做不了
- 已出现过「INIT 推送离线消息 + 前端 `saveMessageBatch` 自带累加」导致红点翻倍，本质是未读归属不清晰

新工程：

- `chat_session_user` 增加 `no_read_count`、`last_read_message_id`（或 `last_read_seq`）
- 服务端维护未读数，客户端只做展示与上报
- 已读用「已读到的最大消息序号」表示，比按条上报更幂等

---

## 4. 离线消息依赖 `user_info.last_off_time`

当前离线消息是「取 `last_off_time` 之后的消息」，超过 3 天截断到最近 3 天。

问题：

- 非正常断连（进程被杀、网络断但心跳没超时）时 `last_off_time` 可能没更新 → 重推已读消息 → 红点复活
- 时间戳做游标不可靠：同一个毫秒多条消息、时钟回拨都会出问题
- 超过 3 天的消息直接丢，无法漫游

新工程：

- 每个会话有单调递增的 `seq`（或消息 ID 本身就单调），客户端上报「本地最大 seq」，服务端拉 (maxSeq, 之后] 的消息
- 离线消息保留期与拉取策略分离：表里消息不截断，拉取时按分页
- 连接断开不应该决定消息是否下发，「拉取」与「在线推送」共用同一套 seq 游标

---

## 5. 文件走 OSS / CDN

当前文件存在服务器本地磁盘（`D:/wechat/`），下载走 `/chat/downloadFile` 接口，鉴权在 Controller 里做。

新工程：

- 文件元信息独立成表（`file_info`：objectKey、大小、类型、封面 objectKey、上传者、状态）
- `chat_message` 只存 `file_id`（或 objectKey），不存路径
- 上传走 OSS 直传（前端拿 STS / 预签名 URL 直传），应用服务器不经手字节流
- 下载走 CDN 签名 URL，有效期短；鉴权在签发 URL 那一步做，CDN 不回源到应用
- 视频封面、图片缩略图在 OSS 侧用图片处理能力生成，不用自己存 `_cover.png`

---

## 6. 其他零散项

- `user_info_beauty` 靓号、`app_update` 灰度等原项目遗留表，新工程如无需求直接不建。
- 群成员关系当前用 `user_contact(contact_type=2)` 复用联系人表，`status` 承担了"在群/退群/被踢"多种含义；新工程建议独立 `group_member` 表，字段语义单一。
- 朋友圈、收藏夹属于新业务域，建议独立表：`moment` / `moment_comment` / `moment_like` / `favorite`，不要往 `chat_message` 上挂。
